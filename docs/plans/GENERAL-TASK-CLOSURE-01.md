# 通用任务闭环与受控外部能力发现开发计划

**文档编号：** GENERAL-TASK-CLOSURE-01

**状态：** `planned / not_implemented`（已规划，尚未实施）

**启动条件：** 使用反馈修复已 Owner 现场验收，并已形成独立收口提交后，**立即启动**。

**第一阶段：** P0 通用外部交接闭环。P0 验收后才做 P1；P1 稳定后才做 P2。

**性质：** 产品与架构开发计划。本文件不实施功能、不改测试、不改运行时代码。

---

## 启动条件（硬约束）

1. 本轮使用反馈修复须完成明日现场验收：WPS / Word / PowerPoint 打开 DOCX/PPTX 并检查中文、换行和溢出；真实 GitHub 网络审计及源码覆盖说明；Electron 会话、姓名纠正、简历确认、失败提示词、重试、协作布局。
2. 现场通过后，该批次须形成**独立提交**（与本计划无关）。提交完成前，不得开始本计划的代码实施。
3. 独立提交完成后，本计划以 **P0 通用外部交接闭环** 为第一项实施内容，立即启动。P0 验收后才做 P1 受控能力发现；P1 稳定后才做 P2 可信工具目录与安装引导。

**不得把 GitHub 审计专项兜底描述为已经覆盖所有任务类型。** 当前 GitHub 公开仓审计只覆盖「远程代码审计」这一类目标；未知任务、跨领域任务（视频、表格、邮件、本机软件操作等）仍可能落入 `general → document`，被错误处理成说明文章。本计划要补的是**通用**交接闭环，而不是再复制一套场景专用逻辑。

---

## 背景与问题

当前已经实现 GitHub 审计专项兜底，以及 `OPTIMAL / BASELINE / LIMITED / UNAVAILABLE` 能力降级框架，但未知任务仍可能进入 `general → document`，被错误处理成说明文章。

能力闭环（CAPABILITY-FALLBACK-CLOSURE-01）解决的是「有什么能力就怎么执行、没有可靠能力就诚实停住」。它**没有**规定：停住之后，如何把任务完整交给其他工具，以及用户把结果带回来之后如何继续检查与修订。GitHub 专项只在代码审计失败时给出可复制提示词；这不能外推为「所有做不了的任务都已经有交接闭环」。

用户要求的最终兜底是：

- 系统无法直接完成任务时，**自动生成**可交给其他工具执行的完整提示词；
- 用户将结果带回后，系统继续检查、生成第二轮优化命令；
- 直到满足验收标准，或用户停止 / 确认接受部分完成。

本计划把上述兜底做成**与任务类型无关**的合同，再在其上做受控能力发现与可信工具目录。实施顺序不可颠倒：先 P0，再 P1，再 P2。

---

## P0：通用外部交接闭环

这是启动后的**第一项**实施内容。不得因建设工具市场（P2）或能力发现（P1）而延误 P0。

### 范围

- **不依赖预先枚举所有任务类型。** 路由与交接包从任务目标抽取结构化需求，而不是维护「视频 / 表格 / 邮件」白名单。
- 从任务目标中提取：
  - 目标成果
  - 必需动作
  - 所需能力
  - 用户材料
  - 输出格式
  - 验收标准
  - 权限与风险
- 当任务处于 `LIMITED`、`UNAVAILABLE`，或能力执行失败且没有可靠自动降级路径时，生成统一「外部执行包」：
  - 原始任务目标
  - 可安全共享的材料说明（只含用户已授权、可外发的范围；不含完整数字之我、未勾选材料、历史对话全文）
  - 可直接复制的提示词
  - 预期交付物
  - 验收清单
  - 禁止编造和未覆盖边界
- 页面提供：
  - 复制提示词
  - 重试当前能力
  - 连接其他能力
  - 导入 / 粘贴外部结果
- 外部结果必须绑定原 Task，不能另建无关任务。
- 系统检查带回的文本、文件和证据；不合格时生成下一轮针对性提示词，直至通过、用户停止或确认接受部分完成。
- **不允许普通写作成果冒充真实执行。** `create_document` / 说明文章不得作为视频剪辑、OCR、发邮件、改本机软件等动作的成功产物。
- GitHub 专项逻辑应逐步复用通用交接合同，不再继续复制场景专用闭环。专项文案可以保留领域细节，但失败态、复制提示词、带回结果、二轮修订须走同一合同。

### 非目标（P0 不做）

- 不扫描本机已安装工具、不查询 MCP 清单（P1）。
- 不建设工具市场、不提供安装引导目录（P2）。
- 不自动下载或安装任何程序。
- 不实现大众社交、匹配、支付、多人协作。

### 与现有代码的衔接（规划级，本文件不改代码）

- 复用既有 `OPTIMAL / BASELINE / LIMITED / UNAVAILABLE` 判定；P0 在 LIMITED / UNAVAILABLE / 无可靠降级的失败态进入交接，而不是再造第二套能力图。
- 复用既有 Task / Job / Artifact 主链：外部结果写入**同一 Task** 的后续材料或成果版本，不新建平行任务。
- GitHub 审计的 `【可复制的提示词】`、失败可重试、带回长文不再当远程拉取，应收敛为通用交接合同的一个领域投影。

## P1：受控能力发现

P0 现场验收通过后再做。根据任务**所需动作**匹配能力，不按工具品牌写死路由。

- 扫描已安装且受支持的本机工具。
- 发现已配置的模型、搜索服务和远程能力。
- 对显式连接的 MCP 服务执行真实能力清单查询。
- 支持标准能力声明：输入、输出、权限、费用、耗时、运行位置、可用性。
- 根据任务所需动作匹配能力，不按工具品牌写死路由。
- 已安装且已登录的工具，可以在用户一次任务级授权后执行。
- 文件修改、网络访问、账号数据、材料上传、付费及对外发送必须分别展示授权范围。
- 授权默认单任务、最小权限、可取消、不可暗中扩大。

P1 发现结果只进入既有能力注册与选择合同，不引入第二套路由状态机。

---

## P2：可信工具目录与安装引导

P1 稳定后再做。不得因建设工具市场而延误 P0。

- 建立经过审核的工具目录，不从任意网页静默下载程序。
- 每个工具记录：
  - 官方发布者与官方地址
  - 能完成的任务
  - 所需权限
  - 是否收费
  - 是否上传用户材料
  - 支持的操作系统
  - 安装及登录状态
- 未安装时提供官方安装入口和非技术化步骤（禁止「运行脚本 / 执行命令」作为普通用户步骤）。
- 安装或登录完成后恢复原任务，不要求用户重新描述。
- 找不到可信工具时，给出具体候选和完整提示词；不得只说「请自行搜索第三方工具」。

---

## 安全边界

全程适用，P0 实施时即须遵守：

- 禁止自动下载安装来源不明的程序。
- 禁止读取浏览器 Cookie 或未授权凭据。
- 禁止把完整数字之我、历史对话或未勾选材料发送给外部工具。
- 外部结果必须经过本地验证，不得因工具声称成功就显示任务完成。
- 无法验证时必须标为「部分完成」或「待用户确认」。
- 高风险动作（文件修改、网络访问、账号数据、材料上传、付费、对外发送）未经该任务明确授权不得执行。

## P0 验收样例

至少覆盖以下未知或跨领域任务。样例用于验收合同，**不是**产品路由白名单；实施不得把这十类写成 `if 视频 then …` 的枚举路由。

1. 视频剪辑
2. 图片批量处理
3. 财务表格分析
4. PDF OCR
5. 邮件发送
6. 日程创建
7. 网页表单填写
8. 数据库迁移
9. 法律材料整理
10. 本机软件操作

每个样例都要验证：

- 不会被写成普通文章冒充执行；
- 能说明缺少的具体能力；
- 能生成针对该任务的完整外部提示词；
- 能接收外部结果并绑定原任务；
- 能检查结果并生成第二轮修订要求；
- 未经授权不会执行高风险动作。
