## 1. Owner 观察到的失败

1. 输入当前讨论较多的短剧「持械入宋」，页面没有找到可用资源，无法表现出对对象的理解，也没有给出有帮助的追问或直接答复。
2. “为你发现”首屏约十余张卡片；向下翻页会停顿约 1～2 分钟才出现下一批。连续 7～8 次后再次长停顿，随后一次涌出一大批内容，滚动节奏不自然。
3. 输入“我想看最近比较热门的短剧，有什么推荐？”等自然语言要求后等待两分钟，页面没有形成结果或明确终态。

Owner 提供的三张截图显示：显式请求被落成“当前没有可用的统一搜索与正文读取能力；未退回旧 RSS 或候选兜底链”，而默认信息流仍能展示卡片。这证明不是整个 Discover 都没有数据，而是显式发现能力判定和连续补量编排错误。

## 2. 根因

### 2.1 显式发现错误绑定到单一供应商协议

验收 userData 的主模型是 DeepSeek Chat。它可以承担理解和推荐判断，但不原生支持当前代码只接受的北京业务空间 Responses 工具协议。`runUnifiedContentSeek` 因此在调用已经配置的托管 Web Discovery 之前直接返回“没有统一搜索能力”。

正确边界应是：Search 是独立、可替换的成熟 Tool，只提供外部候选和证据；当前模型结合 Digital Self 继续承担开放语义理解和最终选择。不得按模型品牌路由，也不得退回几个 RSS 或关键词规则。

### 2.2 翻页把网络/模型补量暴露给滚动

个人 Feed 队列耗尽时，`content.more` 会 `await` 整个后台补量 Promise。一次完整供给、摄入和模型选择需要几十秒到数分钟，因此滚动 IPC 一直不返回；完成后整批结果又被一次性交给页面。

### 2.3 前端递归取页并缺少可接受的第一响应终态

每次 `loadMore` 完成后又立即调用 `maybeLoadMore`。只要页面仍处在近底部，就会自动连续取多页，造成“长时间无变化—突然批量涌出”。显式请求的页面兜底为 250 秒，超过 Owner 等待时长，因而表现成无响应。

## 3. 修复要求

1. 已连接的托管/BYOK Search 可与任意当前主模型组合；Search 不接触完整 Digital Self，不成为最终排序权威。
2. 首屏交付后立即预取下一段；`content.more` 只读取已就绪的唯一 Feed 缓存，任何情况下都不等待网络或模型。
3. 下一段未就绪时立即返回可见“准备中”状态；页面单次只追加一页，不递归吞掉多页。
4. 显式请求 30 秒内必须出现第一批结果、直接答复/必要追问或诚实失败终态，不能静默等待两分钟。
5. 不得为「持械入宋」「短剧」写关键词特例；必须用开放模型理解与可替换搜索能力解决。

## 4. 重新准入条件

## 10. Red 审计与下一条实现主链

失败不在「短剧」或某个站点，而在非 Responses 模型的旧式显式发现链：

```text
意图解释
  → 成熟 Search 与开放目录分叉取候选
  → 每 4 条候选分批做角色判断
  → 确定性代码拼主卡/相关卡
```

这条链没有把完整 Digital Self 交给一次整体最终选择；局部批次也看不到其它候选，容易把“当前批次里像作品的条目”误当成符合用户要求的推荐。继续给 `classifyCandidateRoles` 增加提示词、条件或主题特例，属于同层第三轮修补，按 02 已进入 Red，必须停止。

下一实现改为：

```text
成熟 Search / Source 只提供公共候选与证据
  → 当前主模型一次看完整候选窗口
  → 用户本次要求 + Digital Self + 明确内容控制 + 短期上下文进入同一次最终选择
  → 模型交付有序具体对象及诚实说明
  → runtime 只校验 ID、URL、安全、超时和真实执行事实
```

推荐路线是把非 Responses 当前模型接入与 Responses 工具链相同的“整体最终选择合同”，删除旧分批角色拼装对最终推荐的控制；备选路线是强制用户改用支持 Responses 工具循环的模型，实施更快但破坏模型中立和当前配置兼容，暂不采用。

停止条件：不再增加「短剧」关键词、站点特例、确定性相关性分数或第四轮角色提示词；新主链在开发者正式 Electron 入口同时通过具名作品、宽泛推荐、换题和连续翻页后，才允许再次请 Owner 试用。

## 11. 推荐主链重构实施（2026-11-11）

### 已实现

1. 非 Responses 当前模型的显式发现入口已退出旧 `runContentSeek`。生产调用改为同一当前模型的通用工具环：模型自主调用 `web_search`，Search 只返回真实公共候选；模型用 `present_results` 做整体最终选择。
2. 同一次最终选择上下文包含：用户本次原话、完整 Digital Self、主人明确设置的内容控制、本机短期内容上下文，以及有界的既有 Source 候选窗口。Search 请求仍只发送 query，不上传 Digital Self、偏好或浏览上下文。
3. 所有展示对象必须引用 Search/Source 已返回的 candidate ID。runtime 保留候选的真实标题、URL、来源身份；伪造 candidate ID 会被拒绝并返回同一模型纠正。没有合格对象时允许空交付或直接追问，不退回旧 RSS、开放目录分批角色判断或确定性相关性拼装。
4. 榜单、报道与推荐对象不再混成一个 URL：候选页面本身就是作品/文章/入口时直接交付；公开依据明确支持具体对象但没有对象页时，模型可交付无作品 URL 的推荐对象卡，并单列 `basisSource` 供 UI 显示“看推荐依据”。报道 URL 不再冒充作品 URL。
5. 为兼顾当前主模型的整体判断质量与 30 秒第一终态，候选窗口限制为 6 条既有 Source + 最多 4 次搜索、每次 6 条、总计 30 条；这只是上下文预算，不做主题、关键词或相关性评分。已有候选但第一次空交付时，同一模型在同一工具环内复核一次；runtime 不替它选内容。
