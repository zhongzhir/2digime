## 1. 当前问题复盘与根因

### 1.1 Owner 真机验收观察到的系统性问题

| # | 现象 | 代码证据（只读复盘） |
|---|------|----------------------|
| P1 | 从输入到执行需三步以上确认 | `needs_input`（项目位置卡）→ `needs_capability`（执行能力卡）→ `needs_confirmation`（`execution-confirm-card`：允许/不会执行/范围 dl 列表）→ 才开始；见 `work-ux-stage.js` 阶段派生与 `index.html` 三张卡 |
| P2 | 中栏残留含义不明操作 | `#collab-actions` 内「前往处理」「撤销授权」；`#work-more-menu`「更多」在多阶段为空或装入与当前决策无关动作 |
| P3 | 用户收不到阶段/判断/回应方式信号 | 状态散落在 `#job-status`、决策区、时间线三处；「部分满足验收要求」等系统词直接可见 |
| P4 | Digital Me 未起 AI CTO 作用 | `cto-review.ts` 全部结论由 verifier 布尔检查 + 模板字符串拼接生成（`report = [...].join('')`），无模型参与语义分析 |
| P5 | 用户意见直通 Coding Agent | `runCtoConfirmContinue`：`revisionRequest = directive + '\n\n【用户补充意见】\n' + userText` 直接发 `work.reviseArtifact`，Digital Me 不先回应 |
| P6 | 任何输入默认触发修改 | `routeWorkNaturalLanguage` 在 `activeArtifactId` 存在时一律 `revise`，无「提问/讨论/查询状态」分支（除硬编码暂停正则） |
| P7 | 重复失败不识别、无根因诊断 | `job-runner.ts` 无连续失败计数；失败后 UI 仅给「重试」与泛化解释；六轮失败后用户仍不知项目能否运行 |

### 1.2 根因（按层）

1. **产品层**：把「内部对象生命周期」直接映射成了「用户确认步骤」。项目位置、执行能力、执行范围是运行时事实，被做成三个独立的用户阶段卡，违反规则「内部领域对象不得自然转化为用户操作步骤」。
2. **AI 层**：CTO 环节没有模型。理解（understanding）、验收（cto-review）、修正指令（revisionDirective）全部由规则模板产出，因此只能「转写 verifier」，不能分析、不能对话、不能诊断重复失败。这是 P4/P5/P6/P7 的共同根因。
3. **交互层**：中栏与右栏职责未按「对话 vs 工作区」切分，而是按「旧控件迁移成本」切分，导致协作残留按钮、空「更多」、右栏「请确认成果」空壳。
4. **信息层**：状态是三处独立渲染（任务列表 label、job-status、时间线），没有单一「用户可读的任务阶段」事实投影。

### 1.3 结论

WS-10/10A 的「对话化」只改了排版，没有改变「规则驱动、对象驱动」的本质。本设计要求把 AI 放进闭环中枢，把规则退到边界。

## 2. 目标用户与核心使用场景

- **目标用户**：不读代码、不懂构建/测试/退出码的普通 Owner。以自然语言表达目标，期望像与一位可信 CTO 合作。
- **核心场景**（可泛化，不绑死本次射击游戏 fixture）：
  - S1 从零开发一个小软件（游戏、工具、页面）并试用；
  - S2 对已有项目做一次明确修改并验证；
  - S3 多轮打磨：提意见 → 看新版本 → 再提意见；
  - S4 中途询问「现在到哪一步了 / 为什么失败 / 这个词什么意思」；
  - S5 失败恢复：缺工具、路径错、Agent 实现失败等；
  - S6 完成后的交付：试用、安装、下载、部署、分发。
- **泛化要求**：同一闭环结构未来适用于研究、写作、投资分析等执行者可替换的场景；本设计中「Coding Agent」是「专业执行者」的一个实例。

## 3. 上位产品原则与责任合同

### 3.1 三方责任合同

| 角色 | 负责 | 不负责 |
|------|------|--------|
| **Owner（用户）** | 自然语言表达目标、反馈、决定；确认规划；最终采用 | 阅读 diff / 退出码 / 测试表 / 结构化修订指令；判断专业过程 |
| **Digital Me（AI CTO）** | 理解目标；主动分析项目；形成并维护任务规划；判断准备条件；生成专业指令；指挥执行者；跟踪执行；独立验收；诊断失败（含重复失败）；制定修订方案；自然语言汇报；引导试用/安装/下载/部署/分发；结果与经验回流主体 | 亲自改代码、跑命令（这是执行者职责）；替用户做高风险取舍 |
| **Coding Agent（专业执行者）** | 阅读项目；技术方案细化；修改代码；执行命令与测试；返回成果与工程证据 | 与用户直接对话；决定是否采用；越权操作 |

### 3.2 AI 与规则分工（原则级）

- **AI 负责**：语义理解、意图判断、规划生成与更新、失败诊断、验收结论、面向用户的一切自然语言。
- **规则负责**：权限边界、高风险确认门、数据完整性、必需输出字段校验、超时与成本上限、审计与可恢复性。
- **禁止**：规则/关键词/模板拼接生成 CTO 结论或用户面回复（现 `cto-review.ts` 模式废止，见 §10）。

### 3.3 确认原则

- 每新增一个确认必须证明用户面临**新决策**；无新决策不加确认。
- 普通低风险任务：**输入任务 → 确认规划并开始开发**，两个主要动作，不再单独确认技术细节。
- 仅以下情形追加确认：扩大权限（越出授权目录 / 新增系统访问）、删除或覆盖已有内容、明显成本或时长风险、目标含重大取舍。
- 自然语言「按这个方案开始」与点击「开始开发」语义等价（由 AI 意图判定，见 §9）。

## 4. 端到端任务生命周期

用户可感知阶段（左栏状态、右栏工作区标题均以此为准，唯一事实投影）：

```
理解中 → 规划待确认 → （准备受阻）→ 开发中 → 验收中
   → 需要你回应（未达标/需决策）→ 修订规划待确认 → 开发中（下一轮）
   → 可试用（达标）→ 已采用（结束）
任一执行阶段可进入：已暂停 / 遇到问题（失败恢复）
```

- 内部仍复用既有 Task/Job/Artifact 状态机（§11），**不新增第二状态机**：上述阶段是 Task+Job+plan+review 事实的**派生投影**（同 `deriveWorkUxView` 模式，但输出改为用户可读阶段词）。
- 阶段词是用户文案，禁止 `needs_revision`、`partially_satisfied` 等系统术语外露。

## 5. 五类详细流程

### 5.1 首次开发

```
用户输入自然语言任务
→ Digital Me（AI）分析目标 + 只读扫描项目
→ 中栏：自然语言回应理解、建议、必要问题（至多一次集中提问）
→ 右栏：形成可阅读的《任务规划》卡（目标/交付/路径/边界/准备条件）
→ 用户可继续在中栏修改意见 → AI 回应并更新规划（规划版本 +1）
→ 用户确认（点「开始开发」或说「按这个开始」）
→ Digital Me 生成内部专业指令（不展示给用户，归档可查）
→ Coding Agent 执行 → Digital Me 监督、独立验收
→ 右栏进入成果视图；中栏给出 CTO 结论与下一步引导
→ 用户试用、反馈或采用
```

要点：
- 项目位置、执行能力检查合并进「准备条件」栏目：满足则不打扰；缺失则右栏进入「准备受阻」视图（§6.3），不再是独立确认步骤。
- 「开始开发」按钮在右栏规划卡上，确认对象=**该规划版本**；按钮旁一句话说明确认了什么、将发生什么。

### 5.2 修改循环

```
用户提出意见
→ AI 意图判断（§9）：提问？意见？目标变化？状态询问？暂停？
→ Digital Me 先自然语言回应（理解复述 + 分析 + 影响说明）
→ 若需修改：右栏出现《下一轮修订规划》（改什么/不改什么/预计影响）
→ 用户确认（按钮或自然语言）
→ Digital Me 生成新专业指令 → 同一 Task 新 Job、新 Artifact 版本
→ 再验收、再汇报
```

**任何用户输入都不得默认等于立即执行修改。** 现 `routeWorkNaturalLanguage` 的「有成果即 revise」路由废止。

### 5.3 失败恢复

执行失败后 Digital Me 必须产出一次**诊断回合**（AI 生成，证据折叠）：

1. 归因到失败类别之一：执行工具未安装/未连接；项目路径或类型不正确；权限不足；命令或环境失败；Coding Agent 实现失败；验收证据不足；用户目标仍不明确；其他真实原因。
2. 中栏自然语言说明：完成到了哪里 / 什么没完成 / 为什么失败 / Digital Me 能否自行处理 / 需要用户做什么（具体步骤）/ 做完后怎样继续。
3. **重复失败刹车**：同一归因连续 2 次失败 → 停止同方案重试，AI 必须提出不同方案或明确请求用户决策；连续 3 次 → 强制暂停并给出恢复路径（规则兜底，见 §10）。
4. 输入区始终可用；「重试」只在归因为偶发环境问题时作为快捷方式出现。

### 5.4 达标

- Digital Me 验收通过 → 中栏 CTO 结论（AI 生成：做了什么、怎么验证的、非阻断风险、建议采用）+ 「确认采用」快捷动作在该消息旁。
- 右栏切到「完成阶段」视图：成果、版本、试用方式、安装/下载/部署/分发引导、折叠技术证据。

### 5.5 采用

- 「确认采用」点击前说明：采用的是哪个成果版本；采用=结束本交付循环并沉淀结果；之后如需新工作另建任务。
- 采用后：中栏归档语 + 引导（试用/分发/新任务）；输入区切换为只读提示。
- 采用入口唯一归属中栏 CTO 达标消息（维持 10A 决议）。

## 6. 三栏信息架构

### 6.1 左栏：任务

仅保留：任务名称；用户可读阶段状态（§4 阶段词）；新建任务；任务切换。
删除/禁止：任何操作按钮、技术状态词。

### 6.2 中栏：用户与 Digital Me

唯一持续自然语言交互区。呈现：用户输入；Digital Me 理解与回应；必要澄清；重要进展节点（开始/完成/失败，一条一句）；CTO 判断；失败解释；修订建议；试用与交付引导。

**每条 Digital Me 消息的最低信息合同**（AI 生成时的输出要求，不是模板）：
1. 当前发生了什么；2. Digital Me 的判断；3. 是否需要用户回应；4. 可以如何回应。

底部输入区任务采用前始终可用。快捷按钮只作辅助（确认规划、确认采用、暂停），永不成为唯一入口。

### 6.3 右栏：任务工作区（原「成果」栏重命名）

评估结论：**采纳**改名。「成果」只描述末段，无法承载规划/准备/执行阶段，导致此前空壳「请确认成果」。标题随阶段：

| 阶段 | 右栏内容 |
|------|----------|
| **规划**（任务规划） | 当前规划（目标/预期交付/建议实现路径/重要边界/准备条件清单）+ 主按钮「开始开发」（含确认说明）|
| **准备受阻** | 缺什么（Coding Agent/工具/环境）、安装或连接引导、检测结果、完成后的「继续」入口 |
| **执行**（进行中） | 简洁阶段进展（一行 + 可选文件计数）；当前版本/文件列表；**不**展示修正指令与技术日志 |
| **完成**（成果） | 可交付成果：版本、文件、预览、打开方式；如何试用；安装/下载/部署/分发引导；非阻断风险；折叠「技术证据」|

「开始开发」在右栏规划卡（确认对象是特定规划版本）；「确认采用」在中栏 CTO 达标消息旁（确认对象是特定成果版本 + Digital Me 结论）。

## 7. 各阶段线框与信息层级

```
┌─────────┬──────────────────────────┬─────────────────────┐
│ 任务     │ 与 Digital Me 对话        │ 任务工作区（随阶段） │
│ ─────── │ ┌──────────────────────┐ │ ┌─────────────────┐ │
│ ▸任务A   │ │ 你：做一个……          │ │ │ 任务规划 v2      │ │
│  规划待确认│ │ DM：我理解你要……      │ │ │ 目标 / 交付      │ │
│ ▸任务B   │ │    建议这样做……需确认  │ │ │ 实现路径         │ │
│  开发中  │ │    ┌──────────┐      │ │ │ 边界             │ │
│ [新建任务]│ │    │确认规划(辅)│      │ │ │ 准备条件 ✓✓      │ │
│         │ └────┴──────────┴──────┘ │ │ [开始开发]       │ │
│         │ [输入框………………] [发送]     │ └─────────────────┘ │
└─────────┴──────────────────────────┴─────────────────────┘
```

- 执行阶段右栏：`进行中 · 正在实现游戏主循环（第2轮）` + 文件/版本简表。
- 完成阶段右栏：成果 + 「如何试用」步骤 + `▸ 技术证据（折叠）`。
- 失败时右栏保持上一有效视图 + 顶部一行「遇到问题，见对话区说明」；解释在中栏。
- 信息层级：每屏用户 3 秒内答出「什么阶段/要不要我做事」。层级 = 阶段标题 > 主内容 > 主动作 > 辅助折叠。

## 8. 关键用户文案示例（口径样例，实际由 AI 按情境生成）

- 规划回应：「我理解你想做一个能在浏览器里玩的打飞机小游戏。我建议先做出可运行的基础版：飞机移动、子弹、敌机和计分。右边是我整理的规划，你可以直接改，也可以确认后我就开始开发。」
- 开始开发确认说明：「确认后我会按规划 v2 指挥开发，过程中不需要你盯着；完成或遇到问题我都会在对话里告诉你。」
- 失败解释：「这一轮没有完成。目前游戏页面已经写好，但运行前的依赖安装失败了——这是环境问题，不是代码问题。我可以换一种安装方式再试；如果你愿意，也可以先看看已完成的部分。」
- 重复失败刹车：「同样的原因已经失败两次，我不打算原样再试。我建议改为……；或者你告诉我是否可以……」
- 达标结论：「游戏可以正常运行了：能移动、射击、计分，我做过启动检查。有一点要说明：项目还没有自动测试，以后改动需要再人工确认。建议采用这一版。」
- 采用确认：「你确认采用的是版本 3。采用后这个任务就完成并沉淀结果；之后想再改，随时新建任务即可。」

禁止词表（用户面）：Job、Artifact、verifier、退出码、部分满足验收要求、needs_revision、修正指令、tool_calls 等。

## 9. AI 推理、自然语言回应与结构化输出的边界

### 9.1 意图判定（每次输入先过 AI，不直接建 Job）

AI 结合**整个 Task 上下文**（目标、规划版本、轮次历史、最近失败、当前阶段）输出结构化意图对象（内部）：

```
intent ∈ { discuss_or_question, add_goal_info, modify_plan, confirm_start,
           artifact_feedback, request_explanation, query_status,
           pause_or_cancel, final_adopt, other }
+ confidence + 需要澄清时的追问点
```

- **自然语言输入的意图一律由 AI 结合完整 Task 上下文判断**（目标、当前阶段、规划版本、成果与版本、最近失败、对话历史窗口），不是关键词规则表。
- 低置信度 → 先澄清，不行动。
- **模型不可用时不做任何关键词降级路由**：明确告知理解能力暂时不可用；允许查看/打开成果与明确的暂停、取消按钮操作，但**不得把自然语言转成执行 Job**。原 `routeWorkNaturalLanguage` 关键词路由从主路径与降级路径中一并移除。

### 9.2 AI 输出双轨与确定性文案边界（v0.2 明确）

- **内部结构化**：意图对象、规划对象、验收结论对象、修订指令文本——供运行时与审计。
- **必须由 AI 情境生成、禁止模板拼接**的范围限于：CTO 分析、失败诊断、验收结论、以及情境化的用户回复（现 `report=[...].join('')` 模式在这些环节废止）。
- **可以确定性生成**的范围：固定导航、安全提示、降级提示、结构性文案（阶段标题、按钮文字、空状态、确认说明框架）。二者边界以「是否需要理解当前情境才能写对」为判据。

### 9.4 明确按钮 = 确定性用户决定（v0.2 明确）

用户点击「开始开发」「暂停」「取消」「确认采用」等语义明确的按钮时，直接形成确定性用户决定并走确定性代码路径，**不再额外调用模型解释按钮意图**。自然语言「按这个方案开始」与点击「开始开发」最终落到同一确定性入口，语义一致（III 验证第 5 条）。

### 9.5 项目事实来源（v0.2 明确）

Digital Me **不假装直接读代码**。项目分析所需事实（项目类型、结构、可运行性、改动位置）由只读工具或 Coding Agent preflight 返回，Digital Me 据此形成规划与判断；对话与规划中引用的项目事实必须能追溯到这些返回。

### 9.6 不存储模型隐藏思维链（v0.2 明确）

只落盘以下内容，其余（内部提示词、推理过程、思维链）一律不落盘：

1. 用户与 Digital Me 的可见对话；
2. 意图结论及置信度；
3. 规划版本与确认事实；
4. 必要的证据引用与最终判断。

### 9.7 对话长期保存与模型活跃上下文分离（v0.2 明确）

- 对话事实持久保存于 `Task.meta.conversation`，可追溯、可恢复；
- 每次模型调用的输入采用**可计算的近期窗口/摘要**（由持久对话按固定规则即时推导）；
- 窗口/摘要不单独落盘，**不复制出第二事实源**。

### 9.8 AI 介入点清单

| 环节 | AI 产出 | 规则校验 |
|------|---------|----------|
| 输入理解 | 意图对象 + 回应文本 | 必填字段、长度、敏感操作标记 |
| 任务规划 | 规划文本 + 结构（目标/交付/路径/边界/准备） | 授权目录、禁止操作清单注入 |
| 专业指令 | 给执行者的指令文本 | 边界语句强制附加（不得 commit/push 等） |
| 验收 | CTO 结论 + goalAttained + 建议动作 | 证据完整性（verifier 输出必须在场）、越权硬门 |
| 失败诊断 | 归因 + 解释 + 恢复方案 | 连续失败计数、强制刹车阈值 |

## 10. 规则、运行时、verifier 与 AI CTO 的责任边界

- **verifier / 测试 / diff / 退出状态 = 证据**，输入给 AI CTO；不再直接生成用户可见结论。
- **规则硬门（不可被 AI 覆盖）**：越权修改、未授权 commit/HEAD 移动、目录漂移 → 无论 AI 结论如何，强制进入「需要你回应」并阻断采用建议。
- **规则兜底（AI 失效时）**：模型不可用 → 明示降级；连续失败计数、超时、成本上限由运行时规则执行。
- **审计**：AI 的每次意图判定、规划版本、验收结论均落盘（挂在现有对象上，§11），可追溯。

## 13. 异常设计

- **工具未安装/未连接**：规划阶段即检测并列入准备条件；受阻时右栏给安装/连接引导 + 检测按钮 + 完成后继续入口；中栏同步一句话说明。
- **项目不兼容/路径错误**：AI 在规划阶段只读扫描即报出（「这个文件夹看起来不是一个可以直接修改的项目，因为……我建议……」），不进入执行后才失败。
- **重复失败**：§5.3 刹车规则；诊断必须区分「代码问题 / 环境问题 / 目标问题」，并回答「项目现在到底能不能运行」。
- **模型不可用**：明确告知理解能力暂时不可用（降级提示可确定性生成）；允许查看/打开成果与明确的暂停、取消操作；**不得把自然语言转成执行 Job**，不做关键词降级路由，不假装理解。
- **执行中断/应用重启**：从持久对象重建阶段投影与对话（对话持久化后天然支持）。

## 14. 交付闭环（开发 → 使用）

完成阶段右栏必须回答四件事：**这是什么成果 / 怎么试用 / 怎么留住它（安装/下载/导出）/ 怎么给别人（部署/分发，如适用）**。
- 试用：可运行项目给「试运行」入口 + 启动检查结论；不可运行的说明原因。
- 安装/下载：由 AI 按项目类型生成用户级步骤（人话），不出现原始命令墙；命令折叠在技术证据。
- 部署/分发：本轮仅设计为「引导性说明」，不承诺自动部署（不扩权）。
- 经验回流：采用后由现有 subject 学习链路记录（复用，不新增对象）。

- 最小支持窗口 1280×800；三栏在窄窗切换为「对话优先 + 抽屉式工作区」（沿用现 work-stage-tabs 机制重命名）。

## 16. 验证方案

1. **自动化测试**：阶段投影派生纯函数测试；意图对象结构校验；规则硬门（越权/刹车阈值）测试；渲染层元素归属测试（右栏无采用、中栏无协作残留）。
2. **AI 质量评估退出标准（v0.2 修订，D11-A 适用）**：
   - 真实风格输入不少于 **50 条**（提问/意见/确认/暂停/查询状态/解释/混合）；
   - 讨论、提问、解释、查询状态等**非执行输入误建 Job = 0**；
   - **低置信度输入必须澄清，不得执行**；
   - 总体意图判定正确率 **≥95%**；
   - **模型不可用时不得从自然语言创建 Job**。
   失败诊断用注入式故障 fixture（缺工具、坏路径、构建失败、重复失败）评归因正确性（属 D11-D）。
3. **Owner 真机验收**：隔离 userData；场景=S1 首次开发两步启动、S3 多轮修改（先讨论后修改）、S5 失败恢复（人为断开执行能力）、S6 采用与试用；通过标准=Owner 全程不需要理解任何系统术语即可完成闭环。
